# 在 Agent 情况下如何进行电控开发

> 适用范围：RoboMaster 电控 C/C++ 项目，尤其是使用 Claude Code / Copilot / Cursor / 其他 AI Agent 辅助开发时。  
> 目标：让 Agent 生成的代码不是“能跑就行”的临时代码，而是符合队内规范、可审查、可回滚、可交接、可长期维护的工程代码。
这个东西就是让你知道记得保持写文档的习惯，还有就是ai很容易忘记，如果后面有问题你也能很快找到问题。
那个规范你让ai读然后这个你自己记得先看一眼

---


## 0. 核心结论

使用 Agent 开发时，仓库里必须先准备两类文档：

```text
1. 代码开发规范
2. 技术交付文档
```

推荐放置：

```text
docs/
├─ RoboMaster电控C_Cpp开发规范_v0.1.md
├─ 在Agent情况下如何进行电控开发.md
└─ robots/
   ├─ infantry_2026_技术交付文档.md
   ├─ sentry_2026_技术交付文档.md
   └─ hero_2026_技术交付文档.md
```

或者简单项目可以直接放在仓库根目录：

```text
RoboMaster电控C_Cpp开发规范_v0.1.md
在Agent情况下如何进行电控开发.md
云台LQR控制-技术交付文档.md
```

使用 Agent 前，必须先让 Agent 阅读：

```text
1. RoboMaster电控C_Cpp开发规范_v0.1.md
2. 当前车 / 当前模块的技术交付文档
3. README.md / 架构说明 / 相关模块文档
```

然后再让 Agent 写代码。

## 1. 为什么 Agent 开发更需要文档

Agent 很擅长：

```text
1. 按已有风格补代码
2. 生成重复性结构
3. 写接口注释
4. 补模块说明文档
5. 搜索调用链
6. 根据已有模式改相似模块
7. 总结调试记录
```

但 Agent 也容易犯这些错误：

```text
1. 不知道队内真实代码规范
2. 不知道某台车的机械结构和硬件连接
3. 不知道历史踩坑
4. 不知道某个 PID / LQR 参数从哪里来
5. 不知道哪些文件不能乱改
6. 不知道比赛现场哪些逻辑必须安全优先
7. 容易把“看起来合理”的通用代码写进实时控制链路
```

所以，Agent 不是不能用，而是必须有“上下文入口”。

这个入口就是：

```text
代码规范 + 技术交付文档 + 当前任务说明
```

## 2. 仓库中必须保存的规范文件

### 2.1 强制：保存代码开发规范

每个电控仓库中都应保存一份：

```text
RoboMaster电控C_Cpp开发规范_v0.1.md
```

建议路径：

```text
docs/RoboMaster电控C_Cpp开发规范_v0.1.md
```

如果仓库没有 `docs/`，可以先放根目录。

Agent 开发前必须明确：

```text
你必须先阅读 docs/RoboMaster电控C_Cpp开发规范_v0.1.md，后续所有代码修改必须遵守该规范。
```

---


### 2.2 强制：每台车必须有技术交付文档

每台车、每套核心控制方案，必须有一个技术交付文档。

推荐命名：

```text
云台LQR控制-技术交付文档.md
步兵2026-技术交付文档.md
哨兵2026-技术交付文档.md
英雄发射机构-技术交付文档.md
```

推荐路径：

```text
docs/robots/infantry_2026_技术交付文档.md
docs/robots/sentry_2026_技术交付文档.md
docs/modules/gimbal_lqr_技术交付文档.md
```

技术交付文档不是“展示文档”，而是给后续接手者看的工程说明书。

它必须回答：

```text
1. 这套方案为什么这样设计？
2. 数据流怎么走？
3. 每个模块怎么实现？
4. 关键参数从哪里来？
5. 安全保护在哪里？
6. 踩过哪些坑？
7. 后面还能怎么优化？
8. 后续开发必须遵守哪些约束？
```

## 3. Agent 开发前的固定提示词

每次让 Agent 开发前，建议先给下面这段：

```text
请先阅读以下文档，再开始分析和开发：

1. docs/RoboMaster电控C_Cpp开发规范_v0.1.md
2. docs/robots/当前车辆技术交付文档.md
3. README.md
4. 与本任务相关的 application / modules / bsp 文档

开发要求：
- 必须遵守 RoboMaster 电控 C/C++ 开发规范。
- 不允许 Application 层直接调用 HAL。
- 所有物理量必须明确单位。
- 控制输出必须限幅。
- 涉及电机、云台、底盘、发射的修改必须考虑 zero force / safe mode / 离线保护。
- 修改公共接口时必须同步更新文档。
- 先给出修改计划，不要直接大面积改代码。
```

如果是 Claude Code，可以这样说：

```text
先读 docs/RoboMaster电控C_Cpp开发规范_v0.1.md 和 docs/robots/infantry_2026_技术交付文档.md。
然后帮我实现 xxx。实现前先给计划，确认后再改代码。所有代码必须符合规范。
```

## 4. Agent 开发标准流程

### 4.1 新功能开发流程

```text
1. 写清任务目标
2. Agent 阅读规范和技术文档
3. Agent 搜索相关代码
4. Agent 给出开发计划
5. 人确认方案
6. Agent 小步修改代码
7. 编译 / 静态检查
8. 上车或模块级测试
9. Agent 更新技术文档
10. 提交 commit / 发起 PR
```

不要一上来就说：

```text
帮我把云台改成 LQR
```

更好的任务描述：

```text
目标：将 gimbal yaw 轴从串级 PID 改为误差域 LQR。
约束：
- 保持现有 message_center 接口不变。
- 不修改 bsp/can。
- LQR 输出为力矩，电机模块使用 OPEN_LOOP 透传。
- yaw 误差必须 wrap 到 ±180°。
- 输出限幅 ±5.5 Nm。
- 修改后更新 云台LQR控制-技术交付文档.md。

请先阅读规范和技术交付文档，给出实现计划。
```

---


### 4.2 Bug 修复流程

```text
1. 描述现象
2. 提供复现条件
3. 提供相关日志 / 波形 / 变量
4. Agent 定位可能原因
5. Agent 提出验证方法
6. 人确认后再修改
7. 修改后记录根因和修复方式
```

示例：

```text
现象：yaw 上电后偶发疯转。
复现：上电后进入 GIMBAL_GYRO_MODE，遥控器不动，约 2~5 秒后突然旋转。
已知：RS05 反馈经滑环，CAN temp_count 偶尔为 0。
请阅读技术交付文档的“踩坑”和“安全层”章节，帮我定位可能原因。
先不要改代码，先列出排查路径。
```

---


### 4.3 调参辅助流程

Agent 可以帮助整理调参记录，但不能代替实测。

推荐让 Agent 做：

```text
1. 根据日志整理现象
2. 根据参数变化写调参记录
3. 生成对比表
4. 检查参数是否集中定义
5. 检查单位是否明确
6. 更新技术交付文档
```

不推荐让 Agent 直接：

```text
随便猜一组 PID / LQR 参数
```

调参提交必须记录：

```text
- robot
- board
- motor
- symptom
- change
- result
- test
```

## 5. Agent 必须遵守的开发边界

### 5.1 禁止 Agent 擅自大改架构

以下修改必须先征求人确认：

```text
1. BSP 接口变化
2. Module 公共接口变化
3. message_center 话题名称变化
4. CAN ID / 通信协议变化
5. robot_def.h 中机器人配置变化
6. 电机控制模式变化
7. 任务周期变化
8. 安全保护逻辑变化
9. 大面积格式化
10. 删除历史代码或文档
```

---


### 5.2 禁止 Agent 绕过分层

Agent 不允许为了“快速实现”在 application 中直接写：

```c
HAL_CAN_AddTxMessage(...);
HAL_UART_Transmit(...);
```

正确做法：

```text
Application 调 Module
Module 调 BSP
BSP 调 HAL
```

## 五、安全层

必须写清：

```text
1. 遥控器离线怎么办
2. 电机离线怎么办
3. IMU 离线怎么办
4. 视觉丢失怎么办
5. 裁判系统数据异常怎么办
6. 发射卡弹怎么办
7. 输出限幅在哪里
8. zero force 在哪里执行
9. 上电默认状态是什么
```

## 六、踩过的坑

每个坑建议写：

```text
现象：
根因：
修复：
以后如何避免：
```

示例：

```text

### 6.1 yaw 方向重复取反导致正反馈

现象：上电后 yaw 快速疯转。
根因：IMU 反馈已取反，电机方向宏又取反一次。
修复：只保留反馈取反，删除额外方向宏。
以后如何避免：每个轴只允许一个方向修正点，改前小 K 验向。
```

## 7. 让 Agent 生成技术文档的提示词

技术文档很适合让 Agent 辅助生成，但不能完全脱离实测。

推荐提示词：

```text
请根据当前仓库代码，为 xxx 机器人生成一份技术交付文档。

要求：
1. 参考 docs/RoboMaster电控C_Cpp开发规范_v0.1.md。
2. 参考已有的 云台LQR控制-技术交付文档.md 的结构。
3. 文档面向后续接手代码的人，不写聊天记录。
4. 必须包含：整体设计、数据流、每个子系统实现、关键参数与来源、安全层、踩坑、优化空间、必须遵守的规范、关键常量速查。
5. 对不确定的内容标注“待实测确认”，不要编造。
6. 如果发现代码中参数来源不明，请列为 TODO。
```

如果只生成某个模块的文档：

```text
请为 modules/motor/DJImotor 生成模块技术文档。
要求说明：
- 文件结构
- 对外接口
- 初始化流程
- CAN 收发逻辑
- 电机反馈解析
- 控制输出限幅
- 离线检测
- 使用示例
- 常见错误
```

## 9. Agent 生成代码后的人工检查清单

Agent 写完代码后，人必须检查：

```text
1. 是否符合分层：Application -> Module -> BSP
2. 是否出现 HAL_ 直接调用
3. 物理量单位是否明确
4. 是否有魔法值
5. 电机输出是否限幅
6. 是否考虑离线保护
7. 是否考虑 zero force / safe mode
8. 是否引入全局变量耦合
9. 是否破坏已有接口
10. 是否更新技术文档
11. 是否能编译
12. 是否需要上车验证
```

Agent 可以加速开发，但最终责任仍在人。

## 10. 推荐的仓库 README 提示

可以在仓库 `README.md` 中加入：

```markdown

## Agent 辅助开发说明

本仓库允许使用 AI Agent 辅助开发，但必须遵守以下要求：

1. 开发前阅读 `docs/RoboMaster电控C_Cpp开发规范_v0.1.md`。
2. 开发前阅读当前机器人 / 当前模块的技术交付文档。
3. Agent 不得绕过 BSP / Module / Application 分层。
4. 涉及电机、云台、底盘、发射的修改必须考虑安全模式和离线保护。
5. 修改公共接口、控制参数、安全逻辑后必须同步更新技术文档。
6. Agent 生成的代码必须经过人工 review、编译和实车验证。
```
